## Overview

`@ankarachain/mcp` is a [Model Context Protocol](https://modelcontextprotocol.io) server
that exposes Ankara Chain's deploy and management operations as tools an AI assistant can
call directly. From a conversation, an assistant can deploy a token, mint to an address,
run template-specific lifecycle actions, drive an escrow, manage a pool or a
collateralized loan, and check status, **on EVM networks or on Stellar**, without going
through the CLI's interactive prompts.

It wraps the same `@ankarachain/sdk` classes the CLI uses (`TokenFactory`,
`AssetRegistry`, `EscrowManager`, `RampManager`, `CollateralVault`, `IndexerClient`,
through `EVMAdapter` or `StellarAdapter`), so every tool call goes through the SDK
instead of building raw contract calls.

```
packages/mcp/
├── COVERAGE.md          # SDK method ↔ MCP tool ↔ CLI command audit
└── src/
    ├── index.ts         # tool definitions + handlers + stdio server
    ├── connection.ts    # network → EVMAdapter / StellarAdapter / TokenFactory
    └── templates.ts     # per-template metadata fields + builder for deploy_token
```

## Running the server

```bash
npx -y @ankarachain/mcp
```

Register it with an MCP-compatible client (Claude Desktop, Claude Code, etc.) in the
client's MCP server config:

```json
{
  "mcpServers": {
    "ankarachain": {
      "command": "npx",
      "args": ["-y", "@ankarachain/mcp"]
    }
  }
}
```

The server communicates over stdio, so there's no network port to configure. Each tool
call carries its own connection arguments, so one server instance can work against any
network or wallet:

| Argument | EVM | Stellar |
|---|---|---|
| `network` | optional, defaults to `localhost` (or `polygon`, `polygon-amoy`, `ethereum`, `bnb`, `celo`) | `stellar` or `stellar-testnet` |
| `rpcUrl` | JSON-RPC URL (required) | Soroban RPC URL (optional, defaults per network) |
| `privateKey` | signer key, for write tools | — |
| `stellarSecretKey` | — | signer seed (`S…`), for write tools |

Read-only tools need no key.

<Warning>
Write tools receive the signing key as a plain argument. Only run this server in a trusted
local environment, and use a dedicated key with limited funds, not a primary wallet.
</Warning>

## Tools

42 tools. The full input schema of each is available through the standard MCP
`tools/list` request.

### Tokens

| Tool | Description |
|------|-------------|
| `get_template_fields` | The metadata fields, units, defaults and allowed values for each of the 6 fungible templates. No chain call. |
| `deploy_token` | Deploy any of the 6 fungible templates (farmland, commodity, real-estate, invoice, carbon-credit, mining-rights) with real metadata. Omitted fields use the CLI's defaults. Unknown fields and invalid choices are rejected before anything is sent. |
| `deploy_nft` | Deploy an NFT asset record (`farmland-nft`, `real-estate-nft`, `mining-rights-nft`, `commodity-vault-nft`). |
| `mint_tokens` / `transfer_tokens` / `transfer_nft` | Mint to, or transfer from the signer. |
| `get_token_balance` / `get_token_status` | Balance, and name/symbol/supply/status. |
| `get_asset_details` | Full record: supply, status, country, verifier, metadata version and metadata, plus template state (invoice status/overdue, commodity expiry, carbon retirements, mining license expiry). |
| `asset_action` | Lifecycle and template actions: `set_status`, `set_identity_verifier`, `pause`, `unpause`, `mint`, `update_valuation`, `update_occupancy_status`, `declare_rental_distribution`, `mark_expired`, `mark_funded`, `mark_repaid`, `mark_defaulted`, `retire`, `renew_license`, `mark_license_expired`, `declare_royalty`. |
| `set_asset_status` | Set lifecycle status (`0`=DRAFT … `4`=EXPIRED). |
| `list_deployments` | Tokens a deployer created via `TokenFactory`. |

### Multi-token, pools and oracle

| Tool | Description |
|------|-------------|
| `deploy_batch_token` / `batch_register` / `batch_mint` | Commodity batch (warehouse receipt) contracts. |
| `deploy_pool_vault` / `pool_deposit` / `pool_withdraw` / `get_pool_status` | Multi-asset fund lifecycle. |
| `oracle_set_price` | Post a USD price on a `ManualOracle`. |

### Collateral vault (Stellar)

| Tool | Description |
|------|-------------|
| `vault_open_loan` / `vault_repay_loan` / `vault_liquidate` | Borrower and liquidator actions on a `CollateralVault`. |
| `get_loan` | A loan with its live LTV and liquidation status, or the vault's config if `loanId` is omitted. |

### Escrow

| Tool | Description |
|------|-------------|
| `deploy_escrow` | Deploy a `MilestoneEscrow` from an ordered list of milestone amounts. |
| `fund_escrow` | Fund one milestone, or every unfunded one. On EVM the token approval is done first. Payer only. |
| `mark_milestone_delivered` / `approve_milestone` / `raise_dispute` / `resolve_dispute` / `claim_timelock_release` | Milestone lifecycle. |
| `vote_cancel_escrow` | Mutual cancellation vote. |
| `get_escrow_status` | Parties, token, amounts, flags and every milestone. |

### On-ramp / off-ramp

The off-chain half uses `ManualRampProvider`, a reference implementation. See
[On-Ramp / Off-Ramp](/contracts/ramp-settlement).

| Tool | Description |
|------|-------------|
| `deploy_ramp_settlement` | Deploy a `RampSettlement` contract. |
| `get_ramp_quote` / `initiate_onramp` | Quote and start an on-ramp session. |
| `record_onramp_settlement` | On-chain attestation of an on-ramp mint. |
| `initiate_offramp` / `confirm_offramp_settlement` / `refund_offramp` | Custodied off-ramp lifecycle. |
| `get_ramp_status` | On-chain deposit / record for a reference. |

### Indexer

| Tool | Description |
|------|-------------|
| `query_indexer_events` | Query events from a running `@ankarachain/indexer`. |

For which SDK methods are, and aren't yet, reachable from the MCP server and the CLI, see

## Design notes

- Every tool dispatches through one exported `callTool(name, args)`, which catches handler
  errors and returns `{ content, isError: true }`. A bad call shows up as a readable error
  and never crashes the server. Results are JSON, with bigints rendered as strings.
- The connection layer (`connection.ts`) turns `network` + keys into an `EVMAdapter` or a
  `StellarAdapter`, so most handlers are chain-agnostic. Stellar-only tools fail with a
  clear message on EVM networks.
- The stdio server only starts when the module is run directly, so tool definitions and
  dispatch can be unit tested without a real MCP transport.

## Why an MCP server

The rest of the SDK targets developers writing code. The MCP server targets a different integration path entirely: an AI assistant deploying and operating Ankara Chain contracts on a user's behalf, driven by conversation rather than a script. It's the same underlying contracts and SDK — just a different front door.
